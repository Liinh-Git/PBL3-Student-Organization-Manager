# Contract Conventions

## Purpose

This document defines naming conventions and design rules for all DTOs/contracts in the PBL3 Student Organization Manager system.

## DTO Naming Conventions

### Request DTOs
- **Pattern**: `{Action}{Entity}Request`
- **Examples**:
  - `LoginRequest`
  - `RegisterRequest`
  - `CreateOrganizationRequest`
  - `UpdateEventRequest`
  - `AddMemberRequest`
  - `ReviewRequestRequest`

### Response DTOs
- **Pattern**: `{Entity}Dto` or `{Purpose}Response`
- **Examples**:
  - `UserDto`
  - `OrganizationDto`
  - `EventDto`
  - `MemberDto`
  - `AuthTokenResponse`
  - `MyPermissionsResponse`
  - `UnreadCountResponse`

### Summary DTOs
- **Pattern**: `{Entity}SummaryDto`
- **Purpose**: Lightweight version of full DTO for list views
- **Examples**:
  - `OrganizationSummaryDto` (for list of orgs)
  - `EventSummaryDto` (for list of events)

### Public DTOs
- **Pattern**: `{Entity}PublicDto` or `{Entity}PublicOverviewDto`
- **Purpose**: Public-facing version with limited fields
- **Examples**:
  - `OrganizationPublicOverviewDto`
  - `EventPublicDto`

## Field Naming Conventions

### DateTime Fields
- **Rule**: All datetime fields must be UTC and named with `Utc` suffix
- **Examples**:
  - `CreatedAtUtc`
  - `UpdatedAtUtc`
  - `JoinedAtUtc`
  - `StartDateUtc` (if time component is included)
  - `StartDate` (if date-only, but still stored as UTC)

### ID Fields
- **Rule**: Use `{Entity}Id` pattern for foreign keys
- **Examples**:
  - `UserId`
  - `OrganizationId`
  - `EventId`
  - `MemberId`
  - `DepartmentId`

### Enum Fields
- **Rule**: Enums must serialize as strings, not integers
- **Examples**:
  - `Status: "Active"` (not `Status: 0`)
  - `Visibility: "Public"` (not `Visibility: 0`)
  - `Priority: "High"` (not `Priority: 2`)

### Optional Fields
- **Rule**: Use nullable types for optional fields. Do not use default values to indicate absence.
- **Examples**:
  - `string? Description` (not `string Description = ""`)
  - `int? TargetParticipants` (not `int TargetParticipants = 0`)
  - `decimal? Budget` (not `decimal Budget = 0`)

## Design Rules

### 1. No Entity Exposure
- **Rule**: Never expose EF entities directly in API responses
- **Reason**: Entities contain navigation properties, EF tracking, and internal state
- **Solution**: Always map entities to DTOs

### 2. No EF References
- **Rule**: Contracts must not reference `DbContext`, `DbSet`, or navigation properties
- **Reason**: Contracts are pure data shapes, not domain models
- **Solution**: Use simple properties only (primitives, strings, lists of DTOs)

### 3. No Fake/Default Values
- **Rule**: If a field is missing, return `null` or omit it. Do not invent fake data.
- **Examples**:
  - ❌ `Budget = 0` when budget is not set
  - ✅ `Budget = null` when budget is not set
  - ❌ `AverageRating = 0` when no ratings exist
  - ✅ `AverageRating = null` when no ratings exist

### 4. UTC Datetime Rule
- **Rule**: All datetime fields must be UTC
- **Reason**: Avoid timezone confusion, ensure consistent sorting/filtering
- **Solution**: Use `DateTime.UtcNow` in backend, name fields with `Utc` suffix

### 5. Enum String Rule
- **Rule**: All enums must serialize as strings
- **Reason**: Easier to read, debug, and extend
- **Solution**: Configure JSON serializer to use string enum converter

### 6. Optional Field Rule
- **Rule**: Use nullable types for optional fields
- **Reason**: Distinguish between "not set" and "set to default value"
- **Solution**: Use `string?`, `int?`, `decimal?`, etc.

## Validation Rules

### Request DTOs
- **Required fields**: Use `[Required]` attribute or FluentValidation
- **String length**: Use `[MaxLength]` or FluentValidation
- **Email format**: Use `[EmailAddress]` or FluentValidation
- **Range validation**: Use `[Range]` or FluentValidation

### Response DTOs
- **No validation**: Response DTOs do not need validation attributes
- **Reason**: Responses are generated by backend, not user input

## Mapping Rules

### Entity → DTO
- **Rule**: Map entity properties to DTO properties explicitly
- **Tool**: Use manual mapping or AutoMapper
- **Example**:
  ```csharp
  var dto = new UserDto
  {
      Id = user.Id,
      FullName = user.FullName,
      Email = user.Email,
      Status = user.Status.ToString(), // Enum to string
      CreatedAtUtc = user.CreatedAt
  };
  ```

### DTO → Entity
- **Rule**: Map DTO properties to entity properties explicitly
- **Caution**: Never map `Id`, `CreatedAt`, `UpdatedAt` from request DTOs
- **Example**:
  ```csharp
  user.FullName = request.FullName;
  user.Email = request.Email;
  // Do NOT set user.Id, user.CreatedAt, user.UpdatedAt from request
  ```

## List Response Pattern

### Pattern
- **Wrapper**: `ApiResponse<ListResponse<TDto>>`
- **Example**:
  ```csharp
  ApiResponse<ListResponse<MemberDto>>
  {
      Success = true,
      Data = new ListResponse<MemberDto>
      {
          Items = memberDtos,
          TotalCount = 50,
          Page = 1,
          PageSize = 20
      }
  }
  ```

### Frontend Handling
- **Service**: Returns `ListResponse<TDto>`
- **Adapter**: Transforms `TDto` to `ViewModel`
- **Page**: Renders list and pagination controls

## Error Response Pattern

### Pattern
- **Wrapper**: `ApiResponse<T>` with `Success = false`
- **Example**:
  ```csharp
  ApiResponse<UserDto>
  {
      Success = false,
      Message = "User not found",
      Errors = ["Invalid user ID"],
      TraceId = "abc123"
  }
  ```

### Frontend Handling
- **Service**: Throws error or returns null
- **Page**: Displays error message or `<ErrorState />`
